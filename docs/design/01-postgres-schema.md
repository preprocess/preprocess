# 01. Postgres schema (build step 1)

Scope: build step 1. Organizations, members, fixed roles (Owner, Admin, Member), groups, per-agent grants, API keys, encrypted secrets, the case index, and tenant isolation. Audit tables are in [02](02-audit-chain.md); secret delivery is in [03](03-secret-delivery.md).

## Decision

- **Better Auth owns identity.** `user`, `session`, `account`, `verification` (core), `organization`, `member`, `invitation` (organization plugin) and `apikey` (API key plugin) are generated by Better Auth's CLI into `packages/db/src/schema/auth.ts` and migrated by Drizzle with everything else. We do not hand-edit their shape; we add columns only through Better Auth's `additionalFields`.
- **Fixed roles are Better Auth's member roles.** `member.role` is exactly `owner | admin | member`, which are the plugin's defaults, so no custom access-control config is needed for the three fixed roles. Custom roles are paid and not in this step.
- **Groups are ours, not Better Auth teams.** The teams feature has no per-agent grants and no notion of the Developers group, and our grant, routing and tagging rules would all live outside it anyway. Our `groups` and `group_members` tables reference Better Auth's `organization` and `user`.
- **Every tenant row carries `organization_id`**, is reached through one data layer that refuses to run without an organization, and is protected by RLS as a backstop.
- **IDs** are text with a type prefix and a time-ordered body (`org_…`, `grp_…`, `case_…`), matching Better Auth's text ids and readable in logs. Generated in the app.

## Data layer and RLS

Two Hyperdrive configs over two Postgres login roles:

| Binding | Role | RLS | Used by |
|---|---|---|---|
| `DB` | `preprocess_app` | Enforced (no `BYPASSRLS`, not table owner) | Everything tenant-scoped, through `withOrg` |
| `DB_SYSTEM` | `preprocess_system` | Bypassed | Better Auth's adapter, and `withoutOrg(reason, fn)` |

Migrations run as `preprocess_migrator`, which owns the tables.

```ts
// packages/db/src/client.ts — the only exports product code may use
export type OrgId = string & { readonly __brand: "OrgId" };

export function withOrg<T>(env: Env, org: OrgId, fn: (tx: Tx) => Promise<T>): Promise<T>;
// BEGIN; SELECT set_config('app.org_id', $org, true); fn(tx); COMMIT

export function withoutOrg<T>(env: Env, reason: string, fn: (tx: SystemTx) => Promise<T>): Promise<T>;
// logs { escape: "withoutOrg", reason } as a wide-event field; lint allows it only in files listed in an allowlist
```

- `set_config(..., true)` is transaction-local, so it is safe under Hyperdrive's transaction pooling. Every tenant query therefore runs inside a transaction, which Hyperdrive does not cache; that is acceptable for this data.
- The organization comes from the path (`/v1/orgs/{org}/…`) or the credential, checked against the caller's membership or key, then branded as `OrgId`. No "current organization" preference is read.
- Lint: importing `DB_SYSTEM` outside `packages/db` and `packages/auth` fails; a Queue consumer or Workflow that calls the data layer without an `OrgId` fails.
- Policy, applied to every table with `organization_id`:

```sql
ALTER TABLE groups ENABLE ROW LEVEL SECURITY;
ALTER TABLE groups FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant ON groups
  USING (organization_id = current_setting('app.org_id', true))
  WITH CHECK (organization_id = current_setting('app.org_id', true));
```

Better Auth's `organization`, `member`, `invitation` and `apikey` rows get the same policy keyed on their organization column; Better Auth itself reaches them through `DB_SYSTEM`. `user`, `session`, `account` and `verification` are not tenant rows (a user belongs to many organizations) and have no RLS.

Required tests (tenant isolation is a required-test area, see AGENTS.md): one Vitest file per tenant table that seeds two organizations and asserts that `withOrg(A)` cannot read, update or insert B's rows, and that a raw query on `DB` without `app.org_id` returns nothing.

## Tables (Drizzle)

Better Auth tables are generated; only our additions are shown.

```ts
// Better Auth additionalFields
organization: { slug: text unique, createdBy: text }   // slug already exists in the plugin; listed for clarity
apikey:       { organizationId: text not null }         // see Still to verify, 1

// packages/db/src/schema/access.ts
export const groups = pgTable("groups", {
  id: text().primaryKey(),                              // grp_…
  organizationId: text().notNull().references(() => organization.id, { onDelete: "cascade" }),
  slug: text().notNull(),                               // what agent code names: "legal", "ap-team"
  name: text().notNull(),
  description: text(),                                  // shown to the agent (doc 06)
  isDevelopers: boolean().notNull().default(false),     // exactly one per org, created with the org, undeletable
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  unique().on(t.organizationId, t.slug),
  uniqueIndex("one_developers_group").on(t.organizationId).where(sql`is_developers`),
]);

export const groupMembers = pgTable("group_members", {
  organizationId: text().notNull(),
  groupId: text().notNull().references(() => groups.id, { onDelete: "cascade" }),
  userId: text().notNull().references(() => user.id, { onDelete: "cascade" }),
  addedAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
}, (t) => [primaryKey({ columns: [t.groupId, t.userId] })]);
// A trigger checks the user is a member of the organization.

export const agents = pgTable("agents", {            // rows created by first deploy (step 2); here so grants can reference it
  id: text().primaryKey(),                             // agt_…
  organizationId: text().notNull().references(() => organization.id, { onDelete: "cascade" }),
  slug: text().notNull(),
  archivedAt: timestamp({ withTimezone: true }),
}, (t) => [unique().on(t.organizationId, t.slug)]);

export const agentAccess = pgEnum("agent_access", ["operator", "viewer"]);
export const agentGrants = pgTable("agent_grants", {
  organizationId: text().notNull(),
  agentId: text().notNull().references(() => agents.id, { onDelete: "cascade" }),
  groupId: text().notNull().references(() => groups.id, { onDelete: "restrict" }),
  access: agentAccess().notNull(),
  grantedBy: text().notNull(),
  grantedAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
}, (t) => [primaryKey({ columns: [t.agentId, t.groupId] })]);
```

Rules the schema encodes:

- No grant to a user. A person gets access only through a group, a group of one if needed. Viewer is a per-agent grant through a group, never an organization role.
- The Developers group is not granted per agent; `isDevelopers` means "manages all agents" and is checked in code.
- Groups named in deployed code (to wait on, tag or approve) are written to `deployment_groups` at deploy (step 2). A deploy **fails** if any of them has no access to the agent. There is no case-scoped access.
- A group an agent relies on cannot be deleted, and neither can its grant on that agent, while a live deployment of the agent names it. The API checks `deployment_groups`; `onDelete: "restrict"` on grants is the database half. Downgrading an approving group from operator to viewer is refused the same way, because approvers must be operators.

### Effective access (one function, used by API and inbox)

```ts
type AgentRole = "manage" | "operator" | "viewer" | null;
function agentRole(orgRole: "owner" | "admin" | "member", userGroups: Group[], grants: Grant[]): AgentRole;
// manage if in the Developers group; else the highest of the user's groups' grants; else null.

function canSeeCase(orgRole, role: AgentRole): boolean;
// true for owner and admin on every agent, otherwise role !== null.
// Seeing a case through the owner/admin role does not make someone an operator: Owners and Admins
// view and assign; working a case (edit, rerun, complete) and approving need an operator group.
```

### Secrets (encryption detail; delivery in doc 03)

Envelope encryption with WebCrypto AES-256-GCM:

- **Master key (KEK)** lives in Cloudflare Secrets Store as 32 random bytes, named with a version: `secrets-master-v1`. Only the API Worker and the deploy Workflow bind it. The runtime Worker (Pi Durable) does not, so the Worker that runs the model loop cannot decrypt anything.
- **Per-organization key (DEK)**: 32 random bytes per organization, stored wrapped by the KEK.
- **Values** are encrypted with the DEK; the additional authenticated data is `organization_id|secret_id|version`, so a ciphertext copied to another row or organization fails to decrypt.

```ts
export const orgKeys = pgTable("org_keys", {
  organizationId: text().notNull(),
  version: integer().notNull(),
  masterKeyId: text().notNull(),           // "secrets-master-v1"
  wrappedKey: bytea().notNull(),           // AES-GCM(KEK, DEK), iv prepended
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
  retiredAt: timestamp({ withTimezone: true }),
}, (t) => [primaryKey({ columns: [t.organizationId, t.version] })]);

export const secrets = pgTable("secrets", {
  id: text().primaryKey(),                 // sec_…
  organizationId: text().notNull(),
  name: text().notNull(),                  // ^[A-Z][A-Z0-9_]{0,63}$, becomes the binding name (doc 03)
  version: integer().notNull(),            // bumped on every value write
  keyVersion: integer().notNull(),         // which org_keys row encrypted it
  ciphertext: bytea().notNull(),           // iv || AES-GCM(DEK, value, aad)
  updatedBy: text().notNull(),
  updatedAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
}, (t) => [unique().on(t.organizationId, t.name)]);
```

- Values are write-only through the API; there is no read endpoint.
- Master key rotation: add `secrets-master-v2`, rewrap every `org_keys` row, keep v1 until no row references it. Organization key rotation: new `org_keys` version, re-encrypt that organization's secrets in one job. Neither re-encrypts values with new plaintext, so delivery (doc 03) is unaffected.
- Customer-supplied keys are deferred to a later version; the `org_keys` indirection is what makes them a small addition.
- Which agents' code receives each secret (the guardrail) is `secret_grants`, defined in doc 03 because it is a step 2 table.

### Case index

Per-case state lives in the case Durable Object; Postgres keeps what the inbox and lists need. Created in step 1 so isolation tests cover it; written from step 3.

```ts
export const caseStatus = pgEnum("case_status", ["queued", "running", "waiting", "halted", "completed", "failed", "cancelled"]);
export const haltReason = pgEnum("halt_reason", ["credit_exhausted", "spending_limit_reached"]);
export const caseSource = pgEnum("case_source", ["api", "app", "mcp", "schedule"]);

export const cases = pgTable("cases", {
  id: text().primaryKey(),                              // case_…
  organizationId: text().notNull(),
  agentId: text().notNull().references(() => agents.id),
  deploymentId: text().notNull(),                       // FK added in step 2
  status: caseStatus().notNull(),
  waitingOnGroupId: text().references(() => groups.id, { onDelete: "restrict" }),
  haltReason: haltReason(),                             // set only while status = 'halted' (doc 04)
  source: caseSource().notNull(),
  title: text(),                                        // short label for lists, set by agent code
  costMicroUsd: bigint({ mode: "number" }).notNull().default(0),
  createdBy: text(),                                    // user id, api key id or schedule name
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
  completedAt: timestamp({ withTimezone: true }),
}, (t) => [
  index().on(t.organizationId, t.waitingOnGroupId, t.status),  // inbox
  index().on(t.organizationId, t.agentId, t.createdAt),        // lists
]);

export const caseAssignees = pgTable("case_assignees", {   // assigned through the API or by an Admin in the app
  organizationId: text().notNull(),
  caseId: text().notNull().references(() => cases.id, { onDelete: "cascade" }),
  userId: text().notNull(),                                 // must be able to see the case when assigned
  assignedBy: text().notNull(),                             // user id (Owner/Admin) or API key id; never an agent
  assignedAt: timestamp({ withTimezone: true }).notNull().defaultNow(),
}, (t) => [primaryKey({ columns: [t.caseId, t.userId] }), index().on(t.organizationId, t.userId)]);
```

Assignment is the one place a case names people. Agent code never assigns, and there is no "claim". The assign API is in doc 04.

## Alternatives rejected

- **Better Auth teams as groups.** No per-agent grants, no Developers group, and step 9's synced groups would have to be bolted onto a plugin's table we do not own.
- **One Postgres role with a "bypass" GUC.** Any code could set the GUC; a separate login role makes the escape hatch visible in bindings and lint.
- **Schema-per-organization or database-per-organization.** Tenant rows carry their organization by design; per-tenant schemas multiply migrations and Hyperdrive configs.
- **UUID primary keys.** Better Auth uses text ids; mixing types complicates foreign keys to `user` and `organization`.
- **Per-secret data keys.** One DEK per organization is enough; per-secret keys add rows without a consumer.

## Settled decisions

- Owners and Admins see every agent's cases.
- Cases can be assigned to people with access, through the API or by an Admin; never by agent code, no claim.
- Viewer is only a per-agent grant through a group.
- An assignee who loses access is unassigned, with an audit event.
- A deploy fails on a group without access; groups and grants in use cannot be removed.
- Also settled: API keys are organization-wide and created by Admins; case statuses are queued, running, waiting, completed, failed, cancelled, plus `halted`; hosted Postgres roles come from a one-time bootstrap SQL script run by the migrator role, documented for self-hosters.
- Owners and Admins only view and assign cases they see through their role; working a case needs an operator group.
