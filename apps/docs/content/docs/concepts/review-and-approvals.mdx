title: Review and approvals

  How people check an agent's answers, correct them, and approve what the code
  says needs a person.
---

Review is how people act on a case: they check the agent's answers, correct
them, and decide on what the agent's code asked a person to approve. All of it
happens in the case room's Review tab, and the same actions are in the API and,
except for approving, in MCP.

Review and approvals are separate things. **Review** is checking answers, and
any operator can do it. An **approval** is a requirement the code declares: a
named group, or any operator, has to say yes before something happens.

## Why people review

Agents are useful long before they're right every time. Review lets a team put
an agent to work while a person still checks what matters, and only that: the
schema marks which fields need review, so people check the vendor and the total,
not every line. Every correction is recorded, kept beside the agent's original
answer, and becomes the expected result when the case joins an eval suite.

## What people can do

In the Review tab, each field shows its answer, its status and, when a check
fails, the check's message beside it. People can:

- **Confirm** an answer the agent gave. It becomes `confirmed`.
- **Change** an answer. It becomes `confirmed` too, and fields that depended on
  the old value turn `stale`. They can fill stale fields by hand or leave them
  for the agent.
- **Search** a field's full option list, not only the options the agent narrowed
  it to.
- **Accept a suggestion.** When the agent arrives at a different value for an
  answer a person entered, it never overwrites it: its value waits beside the
  person's, and a person accepts it or leaves it.
- **Rerun** the agent, which finishes the remaining work and sees what people
  changed, or **Complete** the case. See
  [Cases](/concepts/cases#rerun-complete-and-cancel).

Two people editing the same field can't overwrite each other: an edit carries
the version it was made against, and a stale one is refused.

Every action is recorded as a review event: the field, the value before and
after, who did it and when. The agent is told what changed, never who changed
it.

## Where review shows up

Each person's inbox collects what needs them, newest first:

| Item      | When                                                        |
| --------- | ----------------------------------------------------------- |
| Waiting   | A case waits on one of their groups.                        |
| Review    | A case they can work has visible fields waiting for review. |
| Approval  | An approval their group, or any operator, can decide.       |
| Memory    | The agent proposed a rule to remember.                      |
| Mention   | Someone, or the agent, tagged one of their groups.          |
| Assigned  | The case was assigned to them.                              |
| Guardrail | For Owners and Admins: a deployment waits on a guardrail.   |

Waits on a person's groups, tags and assignments are also emailed straight away.
Each person can turn those emails off.

## Approvals

An approval is declared in code, at one of three levels:

| Level      | Declared on           | What waits                                 | `when` receives   |
| ---------- | --------------------- | ------------------------------------------ | ----------------- |
| Completion | `agent({ approval })` | The case's completion.                     | The final answers |
| Field      | A schema field        | That value, or a group's or list's subtree | The answers       |
| Tool       | `tool({ approval })`  | The tool call, before it runs              | The call's input  |

```ts
export default agent({
  instructions: "Pay approved supplier invoices.",
  groups: ["finance-leads"],
  approval: true,
  tools: {
    pay_invoice: tool({
      description: "Pay an invoice",
      input: z.object({ invoiceId: z.string(), amount: z.number() }),
      sideEffects: true,
      approval: { group: "finance-leads", when: (call) => call.amount > 5000 },
      run: async ({ invoiceId, amount }, { env }) =>
        pay(env, invoiceId, amount),
    }),
  },
});
```

`approval: true` means any operator of the agent can approve. `{ group }` names
the group whose members approve; it must be in the agent's `groups`. `when`
decides per case or per call. It must not be async, and if it throws, the
approval applies.

### How each level behaves

**Tool calls.** The call doesn't run. The case waits until a person decides.
Approved, the call runs with exactly the input that was approved, and the agent
continues with its result. Rejected, the call never runs, and the agent
continues knowing it was rejected and why.

**Field values.** When a run ends, each field that needs approval gets a request
for its current value. If the value changes before anyone decides, the request
goes stale and a new one opens for the new value. A rejection keeps the case
waiting with the reason until the value changes and is approved.

**Completion.** When the run ends with everything else in place, the case waits
for approval instead of completing. Approved, it completes. Rejected, it keeps
waiting with the reason, and the next run asks again.

### Who can approve

Approving is a person's act. It needs operator access to the agent (through an
operator group or Developers) and, when the code names a group, membership of
that group. Viewers never approve, API keys can't approve, and the
organization's MCP server leaves approvals out.

A group the code names as an approver must keep operator access to the agent. If
it doesn't have that access when you deploy, the deployment waits until an Admin
grants it; while live code names the group, its access can't be lowered or
removed. A rejection needs a reason, which the agent and the thread see. Every
decision is in the audit log with who made it.

## Proposed memories

While it works, an agent can propose a rule to remember, such as "Northwind
invoices are always in EUR". The proposal shows up in the inbox for a person to
accept or dismiss. Accepted rules go into every later case's context, starting
with the next run.
