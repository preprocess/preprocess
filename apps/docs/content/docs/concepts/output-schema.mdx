  The answer a case produces, declared in code as a tree of fields that the

The output schema is the shape of the answer a case produces: a tree of fields,
declared in your agent's code with `schema` from the SDK. The agent fills the
fields in, people review them in the case room, and the finished answers are
what your systems receive when the case completes.

## Why a schema

A free-text answer is hard to check, hard to correct and hard to hand to another
system. A schema gives each part of the answer a place, a type and a rule:

- the review screen is built from it, so people check one field at a time;
- checks and the success condition decide when the case is done, the same way
  for the agent and for people;
- when a person corrects one field, Preprocess knows which other answers
  depended on it;
- your systems get typed JSON, and every correction becomes an eval case.

## Fields

A schema is a root `s.group` of fields:

| Builder                                     | Holds                                                        |
| ------------------------------------------- | ------------------------------------------------------------ |
| `s.text`, `s.number`, `s.boolean`, `s.date` | A single value.                                              |
| `s.select`, `s.multiselect`                 | One or several options.                                      |
| `s.fetched`                                 | Data your code fetches from inputs the other answers supply. |
| `s.group`                                   | Named fields.                                                |
| `s.list`                                    | Any number of items of one field, often a group.             |

Every field takes a `description` the agent reads, and can take:

- `visible(a)`: whether the field applies, from the other answers. A hidden
  field's value is left out of the output.
- `review`: `"required"`, `"none"`, or a function of the answers. A field
  inherits its group's review setting; the default is `"none"`.
- `approval`: a person approves its value before it stands. See
  [Review and approvals](/concepts/review-and-approvals).
- `invalidates`: paths that go stale when this field changes, for dependencies
  your functions don't read directly.

Paths are dotted, with list indices: `vendor`, `lines[2].glAccount`, or
`lines[*].amount` for every item.

## An example

```ts
const invoice = s.group(
  {
    vendor: s.select({
      description: "Who sent the invoice",
      options: s.source({
        search: async (query, { env }) => erp(env, `/vendors?q=${query}`),
        get: async (ids, { env }) => erp(env, `/vendors?ids=${ids.join(",")}`),
      }),
      review: "required",
    }),
    vendorTerms: s.fetched({
      inputs: (a) => a.get("vendor"),
      fetch: (vendor, { env }) => erp(env, `/vendors/${vendor}/terms`),
    }),
    currency: s.select({ options: ["EUR", "USD", "GBP"] }),
    vatNumber: s.text({ visible: (a) => a.get("currency") === "EUR" }),
    lines: s.list(
      s.group({
        item: s.text(),
        amount: s.number(),
        glAccount: s.select({
          options: (a) => accountsFor(a.get("vendor")),
        }),
      }),
    ),
    total: s.number({
      review: (a) => (Number(a.get("total")) > 10_000 ? "required" : "none"),
    }),
  },
  {
    checks: {
      totalsMatch: (a) =>
        a.sum("lines[*].amount") === a.get("total") || {
          field: "total",
          message: "The lines do not add up to the total",
        },
    },
    success: allReviewed,
  },
);
```

Here the vendor list lives in an ERP and is searched rather than loaded, the
payment terms are fetched once a vendor is chosen, `vatNumber` only appears for
euro invoices, each line's account options depend on the vendor, and the total
needs review only above 10,000.

## Functions run in your code

Every function in the schema (`visible`, `review`, options, `fetch`, checks and
the success condition) runs in your agent's Worker, not in Preprocess. So they
can call your systems with the agent's secrets, through `env`, within the
agent's `network` rules. Preprocess calls them whenever the answers change and
at the end of every run.

Each function gets `a`, an accessor over the current answers: `a.get(path)`,
`a.all(pattern)`, `a.sum(pattern)`, `a.fetched(path)` and, inside a list item,
`a.sibling(name)`. A hidden or empty answer reads as `null`. The accessor
records every path a function reads, and that record is how Preprocess knows
what depends on what: there are no dependency rules to write.

## Options

A select's options can be a fixed array, a function of the answers, or
`s.source({ search, get, page })` for lists too long to load. A source is
searched and paged through the agent's `options_search` and `options_page`
tools, and reviewers can search it in the app. The whole list never enters the
model's context.

For a long list the agent can also call `decide`, which picks from the field's
full option list with the decision model, on the platform side: one option, or
the best few with probabilities.

## Answers and their status

Every answer has a status:

| Status      | Meaning                                                 |
| ----------- | ------------------------------------------------------- |
| empty       | Nobody has answered it.                                 |
| `agent`     | The agent answered it.                                  |
| `confirmed` | A person entered or confirmed it.                       |
| `stale`     | Something it depended on changed after it was answered. |

When an answer changes, every field whose functions read it, and every path it
`invalidates`, is evaluated again. Those that hold a value turn stale, with the
change that caused it. Fetched fields fetch again instead, when their inputs
change. Staleness doesn't cascade further on its own, because a stale value
hasn't changed.

The agent never overwrites a person's answer. If it arrives at a different
value, that value is kept beside the person's as a suggestion, and a person
accepts it or leaves it.

## Checks and the success condition

Both go on the root group.

- **Checks** are named functions over the answers, whoever entered them. Each
  returns `true`, or a message, optionally naming the field it's about. A
  failing check shows beside that field in the Review tab and keeps the case
  waiting.
- **The success condition** says when the case is done. `allReviewed`, from the
  SDK, means every visible field that needs review has a person's answer. Write
  your own to require more, or less.

Without a success condition, a case with passing checks completes when the
agent's run ends, even if fields marked for review haven't been reviewed. Use
`success: allReviewed` when review should hold the case.

## What the agent sees

There's no progressive reveal. The agent's context always holds an overview of
the whole tree and its state, and the agent can read any field in full with
`schema_read`: its description, what its conditions read, its value, status, why
it's hidden or stale, and its fetched data. It answers visible fields in any
order with `schema_answer`, and a value that doesn't fit the field's type or
options is refused.

## The output

What your systems receive (the `answers` on a case and in `case.completed`) is a
nested object of the visible answers, shaped like the schema. A fetched field's
value is its fetched data, after `transform` if it has one:

```json
{
  "vendor": "v_001",
  "vendorTerms": { "paymentDays": 30 },
  "currency": "EUR",
  "vatNumber": "NL853746291B01",
  "lines": [
    {
      "item": "A4 paper, 40 boxes",
      "amount": 812,
      "glAccount": "6100 Office supplies"
    }
  ],
  "total": 812
}
```
