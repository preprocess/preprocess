An agent is the default export of a TypeScript module, written with
`@preprocess/sdk` and kept in your own git repository. It does one kind of job,
such as coding invoices or triaging claims, and every job it does is a
[case](/concepts/cases).

## Why agents are code

Everything that decides how an agent behaves lives in the code: its
instructions, its tools, the answer it must produce, the checks on that answer,
the teams it hands work to and what needs a person's approval. So an agent is
reviewed, versioned and rolled back like the rest of your software, and the app
never has a second, hidden copy of its behavior. People in the app work the
agent's cases; they don't edit the agent.

An agent exists from its first deploy. There is no "new agent" button: the first
`preprocess deploy` or GitHub build under a new name creates it.

## What an agent declares

`agent()` takes one object. Only `instructions` and `tools` are required.

| Option           | What it declares                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| `instructions`   | What the agent does, in plain language. The model reads it at the start of every case.                           |
| `model`          | `deepseek-v4.1-flash` (the default), `deepseek-v4.1-flash-fast`, `kimi-k3.1-pro` or `qwen3.8-27b`.               |
| `reasoning`      | `low`, `medium` (the default) or `high`.                                                                         |
| `tools`          | The tools the model may call, each with a description, a Zod input schema and a `run` function.                  |
| `schema`         | The [output schema](/concepts/output-schema): the answer a case produces, its checks and its success condition.  |
| `groups`         | The groups the code may wait on, tag or name as approvers. See [Groups and access](/concepts/groups-and-access). |
| `approval`       | Whether a person approves the case before it completes. Tools and fields take their own `approval`.              |
| `secrets`        | Organization secrets the code needs. Only the ones an Admin grants reach it.                                     |
| `mcp`            | MCP servers the code calls, by the name the organization registered them under.                                  |
| `network`        | Hosts the code may reach.                                                                                        |
| `schedules`      | Cron schedules that start cases.                                                                                 |
| `ocr`            | Whether files are turned into text before the first model call.                                                  |
| `timeoutSeconds` | The wall clock for each run. A run that passes it fails.                                                         |
| `toolRetries`    | How many times a tool that throws runs again. Tools marked `sideEffects` never do.                               |

  settings, but nothing acts on them yet: tools don't run in a sandbox, and

</Callout>

All three are open-weight models, served through Baseten; there are no
Anthropic, OpenAI or Gemini models and no bring-your-own provider keys. DeepSeek
V4.1 Flash also comes in a fast variant. A deployment built with an older SDK
that names a retired model runs on DeepSeek V4.1 Flash.

<Callout title="Coming">
  Fine-tuning DeepSeek V4.1 Flash and Qwen 3.8 27B on your corrected cases, and
  serving the trained versions, isn't built yet. Kimi K3.1 Pro won't be
  trainable.
</Callout>

`deploy` rejects a definition that breaks these rules (an unknown model, a tool
name that isn't `snake_case`, an approval group missing from `groups`, an
invalid cron) before anything is stored. The [SDK](/sdk) page has the details of
each option.

Settings such as `model`, `reasoning`, `ocr` and `timeoutSeconds` can also live
in `preprocess.config.json` beside your `package.json`; where both set a value,
the file wins and the deploy warns. An organization can set defaults for them,
and people can override them in the app between deployments.

## How an agent runs

The model loop doesn't run in your code. It runs in Preprocess's case runtime,
which calls your code when it needs it:

- once at the start of a case, to read the agent's manifest;
- for every tool call the model makes;
- every time the output schema is evaluated: visibility, options, fetched data,
  checks and the success condition are all functions in your code.

Your code runs as a stateless Worker in its own isolate, one per deployment.
Keep state in your own systems, or in the case's answers.

Besides your tools, the model always has a set of platform tools:

| Tool                             | What it does                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------- |
| `schema_overview`, `schema_read` | Read the whole output schema: fields, descriptions, conditions, values, status. |
| `schema_answer`                  | Answer fields.                                                                  |
| `options_search`, `options_page` | Search and page through a long option list without loading it whole.            |
| `decide`                         | Pick from a field's full option list with the decision model.                   |
| `groups_list`, `tag_group`       | See the groups with access to the agent, and tag one in the case thread.        |
| `memory_propose`                 | Propose a rule to remember across cases, for a person to accept or dismiss.     |

## What the agent can't see

The model sees your tools' names, descriptions, input schemas and results. It
never sees your code or the secrets it uses. Secret values go into your code's
`env` when the runtime loads it, and the SDK removes them from tool results,
errors and console output as a second line of defense. MCP connection tokens
never reach your code at all: calls go through Preprocess, which adds them.

## Archiving

An Owner or Admin can archive an agent. Archiving keeps its deployments, cases
and history, and refuses new deploys under its name.
