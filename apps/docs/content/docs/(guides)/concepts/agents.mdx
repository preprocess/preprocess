An agent is the default export of a TypeScript module written with
`@preprocess/sdk` and kept in your own git repository. Each agent does one kind
of job—coding invoices, triaging claims, reconciling payouts—and every job it
runs is a [case](/concepts/cases).

## Why agents are code

Prompts, tool definitions, output schemas, validation checks, and approval gates
are software, not configuration trivia. When they live in a web UI, changes skip
code review, cannot be tested in pull requests, and drift away from the systems
the agent talks to.

In Preprocess, everything that defines an agent's behavior lives in git:

- its instructions and model choice;
- the tools the model can call and which ones have side effects;
- the [output schema](/concepts/output-schema), checks, and completion rule;
- the teams ([groups](/concepts/groups-and-access)) it hands work to or asks for
  approval;
- the secrets, MCP servers, and outbound network hosts it requires.

Because code is the single source of truth, the app has no "new agent" button
and no prompt editor. An agent comes into existence on its first
`preprocess deploy` or GitHub App build under a new name, and its behavior
changes only when you deploy a new version.

## Models, routing, OCR, and `decide`

Preprocess runs four open-weight agent models, plus two fixed-purpose models for
structured classification (`decide`) and document extraction (`ocr`). There are
no Anthropic, OpenAI, or Gemini models and no bring-your-own LLM provider keys
on Preprocess Cloud.

| Model id                   | Model                      | Served by             | When to pick it                                                              |
| -------------------------- | -------------------------- | --------------------- | ---------------------------------------------------------------------------- |
| `deepseek-v4.1-flash`      | DeepSeek V4.1 Flash        | Baseten               | Default. Strong general accuracy at low token cost for most workflows.       |
| `deepseek-v4.1-flash-fast` | DeepSeek V4.1 Flash (fast) | Baseten (Fast tier)   | Same model on lower-latency capacity when interactive turnaround matters.    |
| `kimi-k3.1-pro`            | Kimi K3.1 Pro              | Baseten               | Harder multi-step reasoning, dense documents, or complex tool orchestration. |
| `qwen3.8-27b`              | Qwen 3.8 27B               | Cloudflare Workers AI | Lighter extraction/routing jobs; runs directly on Workers AI in the account. |

Two operational details matter when choosing a model:

- **Fast-tier fallback.** When Baseten's Fast capacity is short, it serves a
  `deepseek-v4.1-flash-fast` request from standard capacity. The runtime reads
  the model name returned in the response and reprices that turn at the standard
  `deepseek-v4.1-flash` rate so you never pay Fast rates for standard latency.
- **Retired models.** Deployments built with an older SDK that name a retired
  model (`inkling-2-mini` or `inkling-2-small`) automatically route to
  `deepseek-v4.1-flash` so old deployments keep working without redeploying.

Alongside the agent models, the platform routes two fixed-purpose capabilities:

- **`decide`** calls Baseten's `groundhog-1` decision model to pick from a
  field's full option list (returning one option or top candidates with
  probabilities) without stuffing hundreds of options into the agent's context.
- **`ocr`** sends uploaded PDFs and page images (PNG, JPEG, or WebP, up to 50 MB
  and 1,000 pages) to Mistral OCR (`mistral-ocr-4-1`) on Mistral's global API,
  returning per-page Markdown before the first model turn.

On a self-hosted install, Qwen 3.8 27B uses your Cloudflare account's `AI`
binding by default; for Kimi, DeepSeek, `decide`, and OCR, you can supply your
own provider keys (`BASETEN_API_KEY`, `MISTRAL_API_KEY`) or point any model at
your own serving URLs via `MODEL_ENDPOINTS`.

## What an agent declares

`agent()` takes one configuration object. Only `instructions` and `tools` are
required.

| Option           | What it declares                                                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `instructions`   | Plain-language instructions read by the model at the start of every case.                                                              |
| `model`          | `deepseek-v4.1-flash` (default), `deepseek-v4.1-flash-fast`, `kimi-k3.1-pro`, or `qwen3.8-27b`.                                        |
| `reasoning`      | `low`, `medium` (default), or `high`.                                                                                                  |
| `tools`          | Tools the model can call, each with a `description`, Zod `input` schema, `run` handler, and optional `sideEffects` / `approval`.       |
| `schema`         | The [output schema](/concepts/output-schema): structured answers, checks, and success condition.                                       |
| `groups`         | Group slugs the code may wait on, tag, or name as approvers. See [Groups and access](/concepts/groups-and-access).                     |
| `approval`       | Whether a person must approve the case before it completes. Tools and fields take their own `approval`.                                |
| `secrets`        | Organization secret names the code needs. Only secrets an Admin grants are bound into `env`.                                           |
| `mcp`            | Registered organization MCP server slugs the code can call through `ctx.mcp(server)`.                                                  |
| `network`        | Outbound host patterns the code is allowed to `fetch()`.                                                                               |
| `schedules`      | Cron schedules (`name`, 5-field `cron`, optional `timezone` and `previews`) that start cases automatically.                            |
| `ocr`            | When `true`, runs OCR on uploaded files before the first model turn.                                                                   |
| `searchCases`    | When `true`, enables `search_cases` over this agent's completed cases in the same environment. Off by default.                         |
| `sandbox`        | Opt-in Linux container per case (`size`, `preset`, `packages`, `idleTimeoutMinutes`, and `setup` layers). See [Sandbox](/sdk/sandbox). |
| `timeoutSeconds` | Positive integer wall-clock limit per run. Passing it marks the case `failed`.                                                         |
| `toolRetries`    | Whole-number retry count when a non-`sideEffects` tool throws. Defaults to `0`.                                                        |

<Callout title="Coming soon">
  Automatic evals on push (`evals: {onPush}`) are not wired yet—the SDK accepts
  and stores the setting, but pushing code does not trigger eval runs
  automatically. Today, run eval suites manually with `preprocess evals run`.
  (Case sandboxes and custom environments built with `sandbox.setup` are live;
  see [Sandbox](/sdk/sandbox).)
</Callout>

### Validation and setting precedence

The SDK validates your definition before anything is stored. A deploy fails
immediately if `instructions` is empty, `model` or `reasoning` is unknown, a
tool name is not `snake_case`, a secret uses a reserved name (`MCP`, `MODELS`,
or `PREPROCESS_*`), an approval references a group missing from `groups`, or a
schedule has an invalid 5-field cron or unknown IANA timezone.

Operational settings (`model`, `reasoning`, `ocr`, `timeoutSeconds`,
`toolRetries`) can also live in `preprocess.config.json` beside `package.json`.
Where both code and `preprocess.config.json` set a value, the config file wins
and `deploy` prints a warning. Between deployments, an organization can apply
org-wide defaults or dashboard overrides for an agent; promoting a new
deployment resets overrides back to what code and `preprocess.config.json`
declare. See [Deployments](/concepts/deployments#code-is-truth-over-overrides).

## How an agent runs

The model loop never executes inside your bundle. It runs in Preprocess's case
runtime (one Durable Object per case), which loads your deployment's bundle into
a stateless Dynamic Worker isolate and calls it only on well-defined hooks:

- once at case start, to read the manifest;
- on each model tool call (`/tools/{name}`);
- whenever the output schema needs evaluation (`visible`, `review`, dynamic
  `options`, `s.source`, `s.fetched`, `checks`, and `success`).

Because the Dynamic Worker is stateless, never rely on module-level memory
persisting across tool calls or turns. Keep durable state in your own external
systems or in the case's output schema answers.

### Failure modes and isolation boundaries

- **Thrown tools vs. `sideEffects`.** If a tool throws an uncaught error, the
  runtime retries it up to `toolRetries` times. Marking a tool
  `sideEffects: true` disables retries completely—so a payment, email, or ERP
  write is never double-executed on a transient timeout—and tells eval replays
  to reuse the recorded output instead of calling the external system again.
- **Timeouts.** `timeoutSeconds` caps the wall clock of a single run starting
  from the agent's first prompt. Exceeding it marks the case `failed`; an
  operator can still inspect what happened and rerun it.
- **Secret and token isolation.** The model sees tool names, descriptions, input
  schemas, and return values—never your source code or secret values. Granted
  secrets enter only your Dynamic Worker's `env`, and the SDK strips those
  secret strings from tool results, thrown errors, and console output as a
  second line of defense. MCP connection tokens never enter your Worker at all;
  `ctx.mcp(server)` proxies calls through Preprocess, which attaches the
  organization's token.

### Platform tools

Beside the tools you write, the runtime automatically exposes a built-in set of
platform tools to the model:

| Tool                                                      | What it does                                                                                          |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `schema_overview`, `schema_read`                          | Inspect the output schema tree, field descriptions, conditions, values, and status.                   |
| `schema_answer`                                           | Write answers to visible schema fields (validated against field types and options).                   |
| `options_search`, `options_page`                          | Search and paginate a `s.source()` option list without loading it into context.                       |
| `decide`                                                  | Pick from a field's full option list using the `groundhog-1` decision model.                          |
| `groups_list`, `tag_group`                                | List groups with access to the agent and tag a group in the case thread.                              |
| `memory_propose`                                          | Propose a reusable rule across cases for a person to accept or dismiss.                               |
| `search_cases`                                            | Search this agent's completed cases in the same environment (when `searchCases: true`).               |
| `sandbox_exec`, `sandbox_read_file`, `sandbox_write_file` | Run shell commands and read/write files in the case's Linux container (when `sandbox` is configured). |

## Archiving

An Owner or Admin can archive an agent when it is retired. Archiving preserves
its deployments, cases, captures, and audit history, and refuses any new deploys
under its name.
