Preprocess is where applied AI engineers deploy agents written as TypeScript
code, and where the rest of the company works the cases those agents handle. You
write the agent in your own git repository with `@preprocess/sdk`. Preprocess
hosts the runtime, isolates your code, and builds the workspace around it: an
inbox, a case room with the agent's thread, a field-by-field review screen
generated from your output schema, and approvals routed to the right team.

Most production agents stall on everything around the model call: where state
lives while a job waits on a human, how an operator corrects one field without
losing the rest, how finance approves a payout before a tool fires, and how
those corrections turn into regressions tests for the next release. Preprocess
handles that operational layer once so every agent you ship starts with it.

## Agent code vs. the operator workspace

Preprocess draws a hard boundary between **what engineers own in code** and
**what operators do in the app**.

Your agent is a TypeScript module in git. It declares its instructions, its
model, the tools it can call, the shape of the answer it must produce, the
checks that answer has to pass, the teams it can hand work to, and which actions
require human approval. Because behavior lives in code, changes go through pull
requests, code review, preview deployments, and one-click rollbacks. Nobody
edits prompts or wires tools in a dashboard, so production never drifts into a
hidden copy of your agent.

Everything around that module comes from the platform:

- **Deployments.** Every deploy stores an immutable bundle and its manifest.
  Your production branch (`main`) serves live traffic, feature branches produce
  isolated previews, and rolling back means pointing production at an earlier
  deployment.
- **Cases.** An API call, a cron schedule, a person in the app, or an MCP client
  starts a case: one job for one agent, with its own thread, structured answers,
  and lifecycle status.
- **Review and approvals.** Operators inspect the agent's answers field by
  field, correct mistakes, and approve gated tool calls, field values, or
  completions. Every edit is attributed and recorded.
- **Groups and guardrails.** Agent code names teams by group slug, never by
  individual. Secrets, MCP servers, outbound network hosts, and group access are
  gated by organization guardrails before a deployment can serve traffic.
- **Records and evals.** Every run is captured in full (model turns, tool calls,
  tokens, timing), logged, and audited. Completed cases with human corrections
  feed straight into eval suites for the next version.

## Who uses it

| Who       | What they do                                                                  | How they get access                       |
| --------- | ----------------------------------------------------------------------------- | ----------------------------------------- |
| Developer | Writes agents with the SDK, deploys them, sets configuration, and runs evals. | The organization's Developers group       |
| Operator  | Works cases: reviews answers, approves, reruns, and completes them.           | A group with operator access to the agent |
| Viewer    | Reads an agent's cases without changing them.                                 | A group with viewer access to the agent   |

Access splits along two axes that do not overlap. Every person has one
organization **role** (Owner, Admin, or Member) that governs organization-wide
resources like members, secrets, and guardrails. **Groups** govern agents.
Seeing every case as an Admin does not make you an operator; to edit or approve
a case, you still belong to an operator group or Developers. See
[Groups and access](/concepts/groups-and-access).

## Cloud vs. self-hosted

Preprocess runs on Cloudflare: Workers, Durable Objects, R2, Queues, Containers,
and standard Postgres through Hyperdrive, with authentication handled inside
your own Workers by Better Auth. You can run on **Preprocess Cloud** or install
the exact same stack into your own Cloudflare account with `preprocess install`
(or its GitHub Action).

Both deployments come from the same Alchemy infrastructure definition in
`preprocess/preprocess`. The platform enforces a strict portability rule:
product code may only use Cloudflare and Postgres primitives that the
self-hosted installer creates in a customer's account. Cloud-only capabilities
(billing, usage metering, open sign-up, and Preprocess's hosted model keys) sit
behind a single run-mode variable (`PREPROCESS_REGION`, unset in self-hosted
stages) that turns those hosted extras on or off without switching
implementations.

| Concern            | Preprocess Cloud                                                                                                                                                                                                | Self-hosted (`preprocess install`)                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Infrastructure     | Managed in Preprocess's Cloudflare account (`us` region at launch).                                                                                                                                             | Deployed by Alchemy into your own Cloudflare account (Workers Paid) with optional `R2_LOCATION_HINT`.                                                    |
| Database           | Managed PlanetScale Postgres through Hyperdrive.                                                                                                                                                                | Any standard Postgres database Hyperdrive can reach (`DATABASE_URL`).                                                                                    |
| Agent models       | Routed by Preprocess: Kimi K3.1 Pro, DeepSeek V4.1 Flash (normal and fast), and `decide` on Baseten; Qwen 3.8 27B on Cloudflare Workers AI; OCR on Mistral.                                                     | Your own provider keys (`BASETEN_API_KEY`, `MISTRAL_API_KEY`), your account's Workers AI binding (`AI`), or your own serving URLs via `MODEL_ENDPOINTS`. |
| Billing & licenses | Prepaid credits for usage (tokens, OCR, sandboxes, and cases past allowance), monthly billing for active seats and storage over allowance, or an annual commit on Enterprise; monthly spending limits enforced. | Open-source core under Elastic License 2.0; paid compliance features unlocked by an offline signed license key (Ed25519) with zero usage reporting.      |
| Upgrades           | Continuous; every deploy migrates with expand-and-contract safety.                                                                                                                                              | Versioned `v*` releases with upgrade notes; run `preprocess install` to upgrade in place.                                                                |

**When to pick Cloud:** You want to deploy an agent in minutes without managing
a Cloudflare account, Postgres instance, or model provider keys, and you want
pay-as-you-go metering with built-in spending limits.

**When to pick self-hosted:** Your compliance boundary requires case data,
uploaded files, audit logs, and Postgres to stay inside your own Cloudflare
account and database, or you want to point agents at your own model serving
endpoints.
