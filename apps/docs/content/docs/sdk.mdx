## Install

```sh
npm install @preprocess/sdk zod
```

The SDK is MIT licensed and uses [Zod](https://zod.dev) 4 to describe tool
inputs.

## An agent

An agent is the default export of a module. Preprocess bundles that module,
stores the bundle for each deployment, and runs it as a Worker. The model loop
runs on the platform; your code runs only when the model calls one of its tools.

```ts title="src/index.ts"
import { agent, tool } from "@preprocess/sdk";
import { z } from "zod";

export default agent({
  instructions: "You answer stock questions for Acme.",
  model: "deepseek-v4.1-flash",
  secrets: ["ERP_TOKEN"],
  tools: {
    lookup_stock: tool({
      description: "Look up stock for a SKU",
      input: z.object({ sku: z.string() }),
      run: async ({ sku }, { env }) => {
        const response = await fetch(`https://erp.example.com/stock/${sku}`, {
          headers: { authorization: `Bearer ${env.ERP_TOKEN}` },
        });
        return response.json();
      },
    }),
  },
});
```

`model` is one of `kimi-k3.1-pro`, `deepseek-v4.1-flash` (the default),
`deepseek-v4.1-flash-fast` and `qwen3.8-27b`.

Deploy it with `preprocess deploy` (see [CLI](/cli)). The agent's name is your
package.json name without its scope, unless you pass `--agent`.

## Tools

`tool()` takes a `description` the model reads, a Zod `input` schema, and a
`run` function. `run` receives the parsed input and a context with:

- `env`: the secrets the agent declared and was granted;
- `case`: the case being worked, with its `id`;
- `mcp(server)`: a client for an MCP server the agent declared.

Set `sideEffects: true` on a tool that changes something outside Preprocess.
Such a tool is never retried, and when an eval replays a case, it reuses the
result the tool returned instead of calling it again. Set `approval` on a tool a
person must approve before it runs (see [Approvals](#approvals)).

## Secrets

`secrets` lists the organization secrets the code needs. Only the secrets an
Admin has granted to the agent are bound, and the rest are `undefined`. Values
reach only your code. They never reach the model, the case thread, logs or run
capture.

<Callout>
  As a second line of defence, the SDK removes bound values from tool results,
  errors and console output. Code that transforms a value can still leak it, so
  return only what the model needs.
</Callout>

## MCP servers

`mcp` lists the MCP servers the agent uses, by the name the organization
registered them under. Calls go through Preprocess, which adds the
organization's connection token, so your code never holds it.

```ts
export default agent({
  instructions: "You keep CRM contacts current.",
  mcp: ["crm"],
  tools: {
    find_contact: tool({
      description: "Find a CRM contact",
      input: z.object({ q: z.string() }),
      run: ({ q }, ctx) => ctx.mcp("crm").call("search_contacts", { q }),
    }),
  },
});
```

## Output schema

`schema` declares what a case produces: a tree of groups, lists and fields that
people review in the case room. Every function in the schema receives `a`, an
accessor over the answers. It records each path it reads, so Preprocess knows
what to work out again when an answer changes.

```ts
import { agent, schema as s } from "@preprocess/sdk";

export default agent({
  instructions: "Code invoices.",
  schema: s.group(
    {
      vendor: s.select({ options: ["Acme", "Globex"], review: "required" }),
      lines: s.list(
        s.group({
          sku: s.text(),
          amount: s.number(),
        }),
      ),
      total: s.number(),
    },
    {
      checks: {
        totalsMatch: (a) =>
          a.sum("lines[*].amount") === a.get("total") || {
            field: "total",
            message: "Lines do not add up",
          },
      },
    },
  ),
  tools: {},
});
```

- **Fields** are `text`, `number`, `boolean`, `date`, `select`, `multiselect`
  and `fetched`, nested with `group` and `list`. Each takes `description`,
  `visible(a)`, and `review` (`"required"`, `"none"`, or a function of the
  answers).
- **The accessor** has `a.get(path)`, which returns `null` for an empty or
  hidden answer, plus `a.all("lines[*].amount")`, `a.sum(...)`,
  `a.fetched(path)` and `a.sibling(name)` for the field beside this one in a
  list item.
- **Options** for a select are an array, a function of the answers, or
  `s.source({ search, get })` for long lists that are searched and paged rather
  than loaded whole.
- **Fetched fields** declare their `inputs`. The fetch runs again only when
  those inputs change.

## Approvals

`approval` asks a person to approve before something happens:

- on `agent()`, before a case completes;
- on a schema field, before its value stands;
- on `tool()`, before the tool runs.

`true` means any operator can approve. `{ group, when }` names the group that
approves (it must be listed in `groups`) and decides per case or call. `when`
receives the answers, or the tool's input, and must not be async. If it throws,
the approval applies.

## Groups and schedules

`groups` lists the slugs of the organization's groups the agent refers to. In a
tool, `ctx.waitOn(group, { reason })` hands the case to that group and
`ctx.tag(group, message)` notifies it.

`schedules` starts cases on a cron schedule:

```ts
schedules: [{ name: "nightly", cron: "0 2 * * *", text: "Reconcile yesterday's orders" }],
```

## Sandbox

`sandbox` gives each case its own Linux machine. The model can run commands in
it and read and write its files with the `sandbox_exec`, `sandbox_read_file` and
`sandbox_write_file` tools. An agent without `sandbox` has none of them.

```ts
sandbox: {
  size: "small",
  preset: "python-data",
  packages: { apt: ["poppler-utils"], pip: ["pdfplumber"] },
},
```

`size` is required, and a deploy without it fails. Each size is billed per
second while its sandbox is awake:

| Size     | Machine                           | Price per second                  |
| -------- | --------------------------------- | --------------------------------- |
| `small`  | ½ vCPU, 4 GiB memory, 8 GB disk   | $0.00003084 (about $0.11 an hour) |
| `medium` | 1 vCPU, 6 GiB memory, 12 GB disk  | $0.00005376 (about $0.19 an hour) |
| `large`  | 4 vCPU, 12 GiB memory, 20 GB disk | $0.00016710 (about $0.60 an hour) |

Sandbox time counts toward the organization's spending limit and plan credit.
Self-hosted installs run sandboxes in their own Cloudflare account and aren't
billed by Preprocess.

`preset` picks the image:

- `standard`, the default: Debian with bash, curl and git;
- `node`: Node.js 24 and npm;
- `python`: Python 3 and pip;
- `python-data`: `python` with pandas, NumPy, Polars, DuckDB, PyArrow, SciPy,
  Matplotlib and openpyxl.

`packages` installs up to 50 `apt`, `pip` and `npm` packages each time the
sandbox starts. `pip` needs a python preset and `npm` needs `node`.

A sandbox starts on the case's first sandbox call. It sleeps after
`idleTimeoutMinutes` without use (5 by default, at most 60), and it loses its
files when it sleeps. It is destroyed when the case closes, and a single start
lasts at most 2 hours. Its HTTP and HTTPS requests follow the agent's network
rules, and every other connection is blocked.

Owners and Admins can cap the largest size in Settings → Guardrails. A
deployment that asks for a larger size waits until they approve it. You can
override the size for one agent from its settings, up to that cap.

Sandbox calls are captured with the case. When an eval replays a case, it reuses
the captured results and never starts a sandbox.

### Custom environments

On Team and Enterprise plans, `setup` builds a custom environment over the
preset once, when you deploy, so a sandbox doesn't reinstall it every time it
starts:

```ts
sandbox: {
  size: "medium",
  preset: "python",
  setup: {
    packages: { apt: ["poppler-utils"], pip: ["pdfplumber==0.11.4"] },
    run: ["mkdir -p /opt/models && curl -fsSL https://example.com/model.bin -o /opt/models/model.bin"],
    files: { "/etc/parser.toml": "mode = 'strict'" },
    env: { PARSER_CONFIG: "/etc/parser.toml" },
  },
},
```

- `packages` takes the same `apt`, `pip` and `npm` lists as `sandbox.packages`.
- `run` lists up to 50 shell commands, run in order as root in `/workspace`. The
  build stops at the first one that fails. Files they leave in `/workspace`
  belong to the sandbox user afterwards.
- `files` writes up to 100 text files (1 MB in all) before the commands run. A
  relative path is under `/workspace`.
- `env` sets variables for the build and for every command the sandbox runs.

The build follows the agent's network rules, and the deployment shows
**Building** until it finishes. Then it serves, or fails with the build's log.
`preprocess deploy` waits for it. Deploys with the same preset and setup share
one build. When a preset is updated, the environment rebuilds the next time a
sandbox starts.

A custom environment is stored and billed as storage, at the same GB-month rate
as files and logs, while a live deployment uses it. There's no cap on its size,
but it has to fit on the sandbox's disk along with the preset. A deploy fails
when it doesn't, and names the size that would fit. An environment over 1 GB
deploys with a warning: the sandbox downloads it every time it starts or wakes,
at about 25 MB a second.

On other plans, use a preset and `packages`.

## Memory

While it works a case, an agent can propose a rule to remember, such as "Acme
invoices are always in EUR". A person reviews the proposal from the Inbox. Once
they accept it, the agent reads the rule on every later case. An agent holds at
most 100 rules. You can read them in the agent's Memories section and through
the API.

## Searching past cases

With `searchCases: true`, the agent gets a `search_cases` tool. It searches the
agent's own completed cases to see how similar work was resolved. It's off
unless you turn it on, in code or as an override in the agent's settings.

```ts
import { agent } from "@preprocess/sdk";

export default agent({
  instructions: "Extract the invoice fields.",
  searchCases: true,
  tools: {},
});
```

- The search covers only this agent's completed cases in the same organization
  and environment. Production and preview deployments each see their own
  environment's cases, and every deployment of the agent shares them.
- Each result has the case's title, completion date, input text (cut to a few
  thousand characters, plus file names), the agent's final message, its answers
  as people corrected them, and `changed`, the answer paths a person changed.
- A deleted case, or one removed by a retention period, leaves the search.
- In an eval run, the agent sees only cases completed before the case being
  replayed started, with their answers as they stood then. It never sees that
  case, or another case with the same input.
- Search uses Postgres full-text matching on words and numbers. Each search, and
  what it found, is kept in the case's run capture.
