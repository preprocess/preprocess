`@preprocess/sdk` is the TypeScript contract between your git repository and the
Preprocess runtime. Instead of importing a model client or writing a retry loop,
you export one declarative `agent()` module—its instructions, model, tools,
output schema, groups, and approvals. Preprocess bundles that module at deploy
time, runs the model loop inside each case's Durable Object, and invokes your
code inside a stateless Dynamic Worker only when the model calls a tool or the
output schema needs evaluation.

Hand this prompt to your coding agent to write an agent and deploy it.

## Install

```sh
npm install @preprocess/sdk zod
```

The SDK is MIT licensed and uses [Zod](https://zod.dev) 4 to validate tool
inputs and generate the JSON Schema the model sees.

## An agent

An agent is the default export of a TypeScript module. Preprocess bundles that
module, verifies its manifest, stores the immutable bundle for each deployment,
and loads it into an isolated Dynamic Worker on demand. Because the Worker is
stateless, keep durable state in your own external systems or in the case's
output schema.

```ts title="src/index.ts"
import { agent, tool } from "@preprocess/sdk";
import { z } from "zod";

export default agent({
  instructions: "You answer stock questions for Acme.",
  model: "deepseek-v4.1-flash",
  secrets: ["ERP_TOKEN"],
  tools: {
    lookup_stock: tool({
      description: "Look up stock for a SKU",
      input: z.object({ sku: z.string() }),
      run: async ({ sku }, { env }) => {
        const response = await fetch(`https://erp.example.com/stock/${sku}`, {
          headers: { authorization: `Bearer ${env.ERP_TOKEN}` },
        });
        return response.json();
      },
    }),
  },
});
```

`model` is one of `deepseek-v4.1-flash` (the default),
`deepseek-v4.1-flash-fast`, `kimi-k3.1-pro` (served on Baseten), or
`qwen3.8-27b` (served on Cloudflare Workers AI). See
[Agents](/concepts/agents#models-routing-ocr-and-decide) for routing, OCR, and
`decide` details.

Deploy with `preprocess deploy` (see [CLI](/cli)). The agent's slug comes from
your `package.json` name without its scope unless you pass `--agent`.

## Tools

`tool()` defines one capability the model can invoke. It takes a `description`
the model reads, a Zod `input` schema, and a `run` function. `run` receives the
parsed input and a context object with:

- `env`: the secrets the agent declared and an Admin granted (ungranted secrets
  are `undefined`);
- `case`: the current case, with its `id`;
- `mcp(server)`: a client for a declared MCP server;
- `waitOn(group, { reason })` and `tag(group, message)`: hand off or notify a
  declared group.

Set `sideEffects: true` on any tool that changes state outside Preprocess
(sending emails, paying invoices, writing to an ERP). Side-effecting tools are
never retried if they throw, and eval replays reuse their recorded output
instead of calling the external system again. Set `approval` on a tool a person
must approve before `run` executes (see [Approvals](#approvals)).

## Secrets

`secrets` declares the organization secret names your code expects. Only secrets
an Admin has explicitly granted to the agent are bound into `env`; if a
deployment declares an ungranted secret, it enters `waiting` until granted.
Values reach only your Dynamic Worker—never the model, the case thread, logs, or
run capture.

<Callout>
  As a second line of defense, the SDK strips bound secret values from tool
  results, thrown errors, and console output. Code that encodes or transforms a
  secret can still leak it, so return only the fields the model needs.
</Callout>

## MCP servers

`mcp` declares the organization MCP servers your tools can call, by their
registered slug. Calls proxy through Preprocess, which attaches the
organization's connection token on the platform side so your code never holds
it.

```ts
import { agent, tool } from "@preprocess/sdk";
import { z } from "zod";

export default agent({
  instructions: "You keep CRM contacts current.",
  mcp: ["crm"],
  tools: {
    find_contact: tool({
      description: "Find a CRM contact",
      input: z.object({ q: z.string() }),
      run: ({ q }, ctx) => ctx.mcp("crm").call("search_contacts", { q }),
    }),
  },
});
```

## Output schema

`schema` declares the structured answer a case produces: a tree of groups,
lists, and typed fields rendered in the case room's Review tab and emitted on
`case.completed`. Every schema function receives `a`, a tracked accessor over
the answers that records every path it reads so Preprocess automatically knows
which fields turn stale when an answer changes.

```ts
import { agent, allReviewed, schema as s } from "@preprocess/sdk";

export default agent({
  instructions: "Code invoices.",
  schema: s.group(
    {
      vendor: s.select({ options: ["Acme", "Globex"], review: "required" }),
      lines: s.list(
        s.group({
          sku: s.text(),
          amount: s.number(),
        }),
      ),
      total: s.number(),
    },
    {
      checks: {
        totalsMatch: (a) =>
          a.sum("lines[*].amount") === a.get("total") || {
            field: "total",
            message: "Lines do not add up",
          },
      },
      success: allReviewed,
    },
  ),
  tools: {},
});
```

- **Fields** are `text`, `number`, `boolean`, `date`, `select`, `multiselect`,
  and `fetched`, composed with `group` and `list`. Each supports `description`,
  `visible(a)`, `review` (`"required"`, `"none"`, or a function of `a`),
  `approval`, and `invalidates`.
- **The accessor** provides `a.get(path)` (returning `null` for empty or hidden
  fields), `a.all("lines[*].amount")`, `a.sum(...)`, `a.fetched(path)`, and
  `a.sibling(name)` inside a list item.
- **Options** for `select` / `multiselect` take a static array, a function of
  `a`, or `s.source({ search, get, page })` for large catalogs searched on
  demand without loading them into model context.
- **Fetched fields** declare `inputs(a)` and `fetch(inputs, ctx)`. The fetch
  re-runs automatically only when `inputs` changes.

See [Output schema](/concepts/output-schema) for staleness, suggestions, and
checks.

## Approvals

`approval` pauses execution until an eligible person says yes, declared at one
of three levels:

- on `agent()`, before a case transitions to `completed`;
- on a schema field (or group/list), before its value stands;
- on `tool()`, before `run` executes.

`true` allows any operator of the agent to approve. `{ group, when }` restricts
approval to a named group (which must be listed in `groups`) and decides per
case or per call. `when` receives the answers or the tool's input and must be
synchronous—if it throws, the approval fails closed and applies. See
[Review and approvals](/concepts/review-and-approvals).

## Groups and schedules

`groups` lists every organization group slug the agent references. Inside a
tool, `ctx.waitOn(group, { reason })` parks the case on that group when the run
ends, and `ctx.tag(group, message)` notifies it in the thread.

`schedules` starts cases automatically on a 5-field cron schedule (UTC by
default, or any IANA `timezone`; skipped on previews unless `previews: true`):

```ts
schedules: [
  {
    name: "nightly",
    cron: "0 2 * * *",
    text: "Reconcile yesterday's orders",
  },
],
```

## Memory

While working a case, the agent can call `memory_propose` to suggest a rule to
remember across cases, such as `"Acme invoices are always in EUR"`. An operator
accepts or dismisses the proposal from the Inbox. Once accepted, Preprocess
injects the rule into every later case for that agent (up to 100 active rules
per agent). You can inspect or delete rules in the agent's Memories view or
through the API.
